# 03. Каналы: Telegram и MAX

Оба канала реализуют один контракт. Факты об API ниже: Telegram собраны 18.11.2026, MAX сверены с
официальной документацией 21.11.2026 (раздел MAX). API мессенджеров меняются — сверять при изменениях.

## Контракт адаптера канала

```php
interface ChannelInterface
{
    public function id(): string;                                  // 'telegram' | 'max'
    public function checkToken(BotCredentials $bot): BotIdentity;  // имя/username бота или ошибка
    public function discoverChats(BotCredentials $bot, DiscoveryCursor $c): DiscoveryBatch; // для «Подключить чат»
    public function send(BotCredentials $bot, Recipient $to, RenderedMessage $m): SendResult;
    public function limits(): ChannelLimits;                       // длина текста, размер файла, скорость
}
```

`SendResult`: `sent(message_id)` | `retry(after_sec, code)` | `permanent(code)` | `recipient_gone(code)`.
Классификация ошибок — в адаптере; очередь работает только с этими четырьмя исходами.

## Общий сценарий подключения (оба канала)

1. Администратор вставляет токен → `checkToken()` → показываем имя бота, сохраняем токен (только запись).
2. «Подключить чат»: хаб на **5 минут** запускает опрос обновлений бота (`discoverChats`).
   Пользователь за это время добавляет бота в группу/канал или пишет боту в личку (Telegram: `/start`,
   MAX: «Начать»). Найденные чаты показываются списком, администратор отмечает нужные.
3. Опрос прекращается. Постоянный приём апдейтов в v1 не ведётся.
4. Ручной ввод `chat_id` — запасной путь.
5. «Отправить тест» — сообщение во все выбранные чаты бота.

## Telegram Bot API

| Что | Значение |
|---|---|
| Адрес | `https://api.telegram.org/bot<token>/<method>` — **токен в URL**, поэтому URL никогда не логируется |
| Бот | создаётся любым пользователем через @BotFather, модерации нет |
| Проверка токена | `getMe` |
| Получение чатов | `getUpdates` (long polling; не работает, если у бота установлен вебхук — тогда показать ошибку «у бота настроен вебхук, отключите `deleteWebhook`») — события `message`, `my_chat_member` |
| Личные сообщения | бот не может написать первым: пользователь должен нажать `/start` |
| Группы | бота добавляют в группу; в режиме приватности бот видит только команды и упоминания — для `discoverChats` достаточно события `my_chat_member` |
| Отправка текста | `sendMessage`, `parse_mode: HTML`, текст до **4096** символов; подпись к файлу до **1024** |
| Кнопка | `reply_markup.inline_keyboard` с кнопкой `url` |
| Аудио | `sendAudio` (MP3/M4A) или `sendVoice` (OGG/Opus); загрузка до **50 МБ** |
| Лимиты | ~1 сообщение/с в один чат, ~20/мин в группу, ~30/с суммарно на бота |
| 429 | `parameters.retry_after` — ждать указанное число секунд |
| Получатель недоступен | 403 «bot was blocked by the user», 403 «bot was kicked…», 400 «chat not found» → `recipient_gone` |
| Миграция группы | 400 с `parameters.migrate_to_chat_id` → обновить `chat_id` получателя и повторить |

## MAX Bot API

Факты сверены с официальной документацией **21.11.2026**: `https://dev.max.ru/docs-api` (страницы
методов, «Общее описание», «Форматирование», «Клавиатура», «Получение ID чата») и официальная
OpenAPI-схема `max-messenger/api-schema` 0.0.34. **Живая проверка на тестовой станции 21.11.2026**
(этап 3d, реальный тестовый бот): `GET /me`, `GET /updates`, `GET /chats/{chatId}`, `POST /messages`
(в группу по `chat_id` и в диалог по `user_id`), `DELETE /messages`, `GET/POST/DELETE /subscriptions`,
лимит 4000, «бот удалён из группы», «пользователь заблокировал бота». Ниже помечено, что откуда.

| Проверка токена | `GET /me` → `{user_id, first_name, name, username, is_bot, …}`; ошибка — 401 `{code: "verify.token", message: …}` — **подтверждено** |

| События | `bot_added` (`chat_id`, `user`, `is_channel`), `bot_started` (`chat_id` диалога, `user`, `payload`, `user_locale`), `bot_removed`, `user_removed`, `bot_stopped`, `message_created`, … Названия чата в событиях **нет** — **подтверждено** |
| Отправка | `POST /messages?chat_id=…` или `?user_id=…` (`disable_link_preview` — в query); тело: `text` ≤ **4000**, `format` (`html`/`markdown`), `attachments[]`, `notify`; ответ 200 `{message: {recipient, timestamp, body: {mid, seq, text}, sender}}`; ошибки 400/401/403/500 — **подтверждено живым ботом** |
| Лимит 4000 | Считается **длина поля `text` целиком, вместе с HTML-тегами**: текст 4004 символа (видимых 3979) и 4010 символов отклонены с `400 {"code":"proto.payload","message":"Field 'text' size (N) must be at most 4000"}` — **живое, 21.11.2026**. Поэтому рендер мерит блок с тегами и сущностями и держит запас 32 символа |
| Кнопка | вложение `inline_keyboard`; кнопка `type: link` — текст 1..128, URL до 2048; до 210 кнопок, до 30 рядов, 7 в ряд (для `link` — 3) — **подтверждено** |
| Разметка | HTML: `<b>/<strong>`, `<i>/<em>`, `<s>/<del>`, `<u>/<ins>`, `<code>/<pre>`, `<a href>`, `<mark>`, `<h1>…<h5>`, `<blockquote>`; Markdown тоже поддержан — **подтверждено** |
| Аудио | `POST /uploads?type=audio|video|image|file` → `{url, token}`; загрузка по `url` (multipart или resumable), затем вложение `{type: audio, payload: {token}}`; аудио до 256 МБ и 60 мин, файл до 4 ГБ — **подтверждено** |
| Готовность вложения | `attachment.not.ready` (HTTP 200 + `success:false`) → пауза и повтор с ростом интервала — **подтверждено** |
| Удаление | `DELETE /messages?message_id=…`; бот должен быть админом с правом удаления; в диалоге — только свои сообщения, в чате/канале — любые; ≤ 2 удаления/с в один чат; ответ 200 `{success, code, message}`, ошибки 401/403/500 — **подтверждено**. Возрастного лимита в документации **нет** — проверить (Q9) |
| Лимиты | ≤ 2 сообщения/с в один чат; **≤ 30 rps суммарно** на `platform-api2.max.ru` (включая загрузки) — **подтверждено** |
| Ошибки | два формата: 4xx `{code, message}` (POST /messages, GET /me, GET /updates) и HTTP 200 `{success:false, code, message}` (DELETE /messages, subscriptions, …); `code` — машиночитаемый ключ (`not.found`, `chat.denied`, `proto.payload`), `message` — текст, в коды не попадает; 5xx документированного тела не имеет — **подтверждено** |
| Бот удалён из чата | `POST /messages?chat_id=…` → **404** `{"code":"error.not.found","message":"error.not.found"}` — **живое** (бот удалён из группы) |
| Пользователь заблокировал бота | `POST /messages?user_id=…` → **403** `{"code":"chat.denied","message":"Key: error.dialog.suspended, args: [<user_id>,]."}` — **живое** (диалог «приостановлен») |
| Подписка (вебхук) | `POST /subscriptions` → `{"success":true}`; `GET /subscriptions` → `{"subscriptions":[{url,time}]}`; `DELETE /subscriptions?url=…`; **при активной подписке `GET /updates` → 200 и `{"updates":[],"marker":…}`** — молчаливая пустая страница, код ошибки не приходит — **живое, 21.11.2026** |

### Q9 — закрыто на живом боте 21.11.2026

- «Бота удалили из чата» → **404 `error.not.found`** → `recipient_gone`, `max.404.not_found`, чат `gone`.
- «Пользователь заблокировал бота» → **403 `chat.denied`** с `message: "Key: error.dialog.suspended, …"`
  → `recipient_gone`, `max.403.chat_denied`, чат `gone`.
- Вебхук-подписка: `GET /updates` отвечает **200 с пустой страницей**, а не 405; поэтому код
  `max.405.webhook_set` ставится по проверке `GET /subscriptions` на первой пустой странице сеанса
  поиска (матчинг 405 тоже остаётся).
- Удаление свежего сообщения работает (`retracted`), **возрастной лимит не выяснен**: на тестовом
  боте нет сообщения старше суток. Подсказка в интерфейсе так и говорит — «MAX не документирует срок».
- `Retry-After` в 429 за сессию не встретился (ни одного 429) — заголовок читается, но не подтверждён.
- Может ли бот писать первым — не проверялось: бот писал в диалог только после «Начать».
- 5xx и таймауты на живом боте не воспроизводились.

### Корневой сертификат НУЦ Минцифры

- **Источник:** `https://gu-st.ru/content/Other/doc/russiantrustedca.pem` — официальная выдача НУЦ
  Минцифры (тип `application/x-x509-ca-cert`, `Last-Modified: 15.09.2022`,
  `Access-Control-Allow-Origin: *`). В модуле поставляется **только корневой сертификат**
  (из официального файла, байт в байт): `Lib/Channels/Max/certs/russian_trusted_ca.pem`
  (SHA-256 файла `aa800ef345422d6158c6fafe1c06c429dbda21c3df4bb1ccb45a920ec1111399`).
- **Отпечаток SHA-256 (DER, закреплён в коде):**
  - `Russian Trusted Root CA` — `D2:6D:2D:02:31:B7:C3:9F:92:CC:73:85:12:BA:54:10:35:19:E4:40:5D:68:B5:BD:70:3E:97:88:CA:8E:CF:31`
    (до 27.02.2032). Промежуточный `Russian Trusted Sub CA`
    (`BB:BD:E2:10:…:FD:9B`, до 06.03.2027) **не поставляется и не закрепляется**: сервер присылает
    его в handshake, поэтому его ротация не требует новой версии модуля.
- **Проверка цепочки (21.11.2026, станция и рабочая машина):** `platform-api2.max.ru` отдаёт **leaf `*.max.ru` + `Russian Trusted
  Sub CA`** (то есть промежуточный сертификат приходит в handshake); корень `Russian Trusted Root CA` в
  системе отсутствует (curl без bundle падает на `unable to get local issuer certificate`). С
  поставляемым файлом и с собранным bundle `GET /me` отвечает 401 `verify.token`, `verify return
  code: 0` — TLS проходит, отключение проверки не нужно. Так как Sub CA приходит от сервера,
  возможно закрепление **только** Root CA (ротация Sub CA не потребует новой версии модуля); решение
  и минусы — в `Plan/09`, пока поставляются оба.
- **Лицензия:** это публичный сертификат открытого ключа, опубликованный Минцифры именно для
  установки в доверенные хранилища; выдача отдаётся с `Access-Control-Allow-Origin: *`, т.е.
  распространение не ограничено, а сам файл распространяется без изменений. Текста отдельного
  лицензионного соглашения на странице выдачи нет — при смене файла (новый Root CA после 2032)
  перепроверить источник, отпечатки и условия.
- **Как подключается** (`Lib/Channels/Max/MaxCaBundle.php`): bundle = системный CA-файл АТС +
  поставляемый PEM, собирается в `sys_get_temp_dir()/module-messenger-hub-ca-<uid>/<hash>.pem` и
  передаётся **только** транспорту MAX (`CURLOPT_CAINFO`). Telegram и системное хранилище не
  трогаются, `CURLOPT_SSL_VERIFYPEER` всегда `true`.
- **`max_ca_bundle_path`** из настроек заменяет поставляемый файл (например, если MAX перейдёт на
  другой корень); файл должен содержать хотя бы один PEM-сертификат, иначе настройка отклоняется;
  нечитаемый путь — предупреждение в лог и возврат к проверенному поставляемому bundle.
- **Защита от подмены:** каждый сертификат файла сверяется с закреплённым отпечатком. Несовпадение —
  файл не используется вообще (fail-closed): TLS падает штатно с кодом `max.tls.untrusted_ca`,
  в лог пишется `ca_bundle_invalid`. Ошибка TLS — `permanent`, без бесконечных повторов.


## Форматирование

Шаблоны рендерятся в нейтральную разметку (`RenderedMessage`: заголовок, строки «ключ: значение»,
абзацы, цитаты, кнопки, вложения). Адаптер канала превращает её в HTML (Telegram) или HTML (MAX)
и **экранирует** всё, что пришло из данных (имена, тексты расшифровок).
Обрезка под лимит канала: сокращается самый длинный абзац с многоточием; ID и кнопка сохраняются —
правило одно для обоих каналов (`Lib/Channels/TextTruncator.php`).

## Вложения (этап 3a) — решения 21.11.2026

Этап 3a-1 — только backend (без UI и без станции). Ниже — решения по пунктам 3a-1; код им следует.

### 1. Какие события что получают

| Событие | Вложение | Почему |
|---|---|---|
| `core.voicemail` | сам файл голосовой почты | файл и есть сообщение |
| `ai_supervisor.attention_call` | по умолчанию фрагменты вокруг цитат (до 3, `start_ms/end_ms` ±5 с, пересекающиеся склеиваются); весь разговор — только явной опцией правила | фрагменты короткие: меньше трафика и меньше лишней речи в мессенджере |
| `core.missed_call` | **нет** | запись пропущенного — это IVR/приветствие, а не разговор с клиентом; событие про «перезвонить», а не «послушать». Путь из CDR остаётся фактом в журнале АТС, но в мессенджер не уходит |
| остальные | нет | у события нет звука |

`fragments` для голосовой почты = весь файл (времён в событии нет, файл короткий). `fragments` для
`attention_call` без валидных цитат = без вложения (не подменяем выбранную приватность полной записью);
причина — `attachment.quotes_missing`. Опция `recording` отправляет разговор целиком.

### 2. Откуда берётся файл (без правок ядра и модулей-источников)

- **Голосовая почта** — путь из AMI-события `voicemail_end` (`vm-recordingfile`), уже лежит в
  `AST_MONITOR_DIR` (ядро копирует туда запись, `VoiceMailConf::getCopyFilename`).
- **`attention_call`** — по `linkedid` из события через **публичный Core REST v3**:
  `GET /api/v3/cdr/{id}` (если ИИ Супервайзер отдал `recording_access.cdr_id`) либо
  `GET /api/v3/cdr?linkedid=…`; в ответе `download_url`/`playback_url` с одноразовым токеном,
  затем `GET /api/v3/cdr:download?token=…`. Это `read`-путь `/api/v3/cdr` в ключе хаба (Q15;
  playback/download у ядра публичные по токену, ключ нужен для списка/записи CDR). Путь добавляется
  только пока есть включённое правило с `attachments != none` для `attention_call` и включён источник
  ИИ Супервизора; при выключении правила путь снимается (Q15).
  Таблицы и внутренние файлы ИИ Супервизера не читаются. Если ИИ Супервизер вернул `cdr_id` —
  он используется; иначе ищется любой сегмент разговора с записью.
- Путь и URL с токеном живут только в памяти/БД модуля; в логи и коды ошибок не попадают.

### 3. Безопасность пути

- Путь из AMI — недоверенный. `realpath()`, файл должен быть **внутри** allow-list корней, взятых из
  констант ядра (только чтение): `AST_MONITOR_DIR` и соседний `voicemailarchive`
  (`dirname(AST_MONITOR_DIR)/voicemailarchive`). Симлинк наружу, `..`, отсутствующий/нечитаемый файл,
  пустой файл, исходник больше 1 ГиБ → без вложения, код `attachment.path_rejected` /
  `attachment.path_missing`; путь не попадает ни в лог, ни в код, ни в REST.
- **Probe-события** (`payload.probe = true`) видят только собственный каталог модуля
  `<module>/tmp/probe`; реальные записи им недоступны, и наоборот — обычное событие не может взять
  файл из probe-каталога.

### 4. Конвертация

- `ffmpeg` → `sox -C` → `sox` (в WAV) + `lame`; MP3, mono, 32 кбит/с (речь, маленький файл), фрагменты
  режутся тем же проходом (`-ss`/`-t`).
- Запуск только `proc_open` с **массивом аргументов** (без shell-строки), с `nice`, жёстким таймаутом
  (`proc_terminate`, затем `SIGKILL`), `-nostdin`. Вывод — только в `<module>/tmp/attachments` (0700).
- Нет инструмента → `attachment.converter_missing`, текст уходит без аудио. Временные файлы удаляются после
  доставки/окончательного отказа; уборщик сносит забытое старше N часов.
- Проверка инструментов в рантайме (Q7), без установки пакетов и без правок системы.

### 5. Лимиты и деградация

- После конвертации проверяются размер и (если известна) длительность: Telegram 50 МБ, MAX 256 МБ / 60 мин.
  Превышение/ошибка конвертации → этот фрагмент без файла.
- **Текст никогда не ждёт аудио.** Сначала уходит текст. Быстрый локальный preflight (файл существует,
  allow-list, инструмент есть) может заранее сказать «аудио не будет» — тогда строка
  «Запись доступна в АТС.» (при `pbx_public_url` — с кнопкой карточки звонка) добавляется **в текст**.
  Если отказ выяснился позже (CDR/конвертация/размер), в тот же чат уходит **отдельная короткая
  строка-примечание** тем же механизмом частей; текст не редактируется и не дублируется.
- Аудио — **отдельное сообщение после текста** с короткой подписью (заголовок события + время;
  для фрагмента — ещё и диапазон), экранированной каналом. Текст и подпись маскируются по правилу.

### 6. Приватность

- Опция правила `options.attachments`: `none | fragments | recording`, по умолчанию **`none`** для новых
  **и существующих** правил. Легаси-значение `true` (булев API этапа 2) трактуется как `none`, пока
  администратор явно не выберет режим в 3a-2: миграция не должна начать рассылать записи сама.
- Маскирование телефона действует на текст и подписи; probe-события могут ссылаться только на
  probe-каталог модуля.
- Включать вложения можно только для событий, у которых есть звук; в UI 3a-2 опция показывается только для них.

### 7. Доставка по частям (queue-resilience)

- Одна строка Outbox = текст + N аудио-частей (+ при необходимости строка-примечание). Прогресс
  каждой части (`pending/sending/sent/skipped`, id, код, MAX-токен) хранится в
  `delivery_parts_json`; повтор **никогда** не отправляет уже отправленный текст или часть.
- **Текст и примечание:** неизвестный исход (таймаут/обрыв после отправки) — один повтор, затем
  `failed`; ошибка до отправки (`http.connect_failed`) — обычный повтор. Состояние `sending`, сохранённое
  перед вызовом, после перезапуска/истечения лизинга не переводится в `pending` автоматически: это
  неизвестный исход и он идёт по правилу одного повтора. **Аудио-части:** at-most-once — неизвестный
  исход → `attachment.uncertain` и пропуск; явный `retry` (429/5xx) повторяется по своей политике,
  исчерпание попыток части → `skipped` + примечание, строка остаётся `sent`.
- Конвертация — в воркере доставки, но лизинг строки **продлевается** перед подготовкой и во время неё,
  поэтому долгая запись не даёт второму воркеру отправить ту же строку. Подготовленные файлы кэшируются
  на событие (`cache_key` = событие + режим + источник + фрагменты): одна конвертация на все чаты.
- MAX `attachment.not.ready`: повтор с **тем же** upload-токеном, паузы 5/10/20 с (не больше 3), затем
  часть пропускается и уходит строка-примечание. Telegram 413 / MAX-размер → часть `skipped` (`permanent`),
  строка всё равно `sent`.
- Сбой источника/канала не мешает остальным: аудио-часть падает — текст уже доставлен, остальные чаты живут.

### 8. Удаление (retract)

- `RetractionService` удаляет **каждый** сохранённый id (текст + все части + примечание) по одному
  `deleteMessage`; на каждое удаление — отдельная резервация `RateLimiter` (MAX ≤ 2/с в чат), иначе строка
  откладывается. Прогресс (`done`) хранится в `retract_progress_json`, повтор не удаляет уже удалённое.
- Частичный/permanent отказ (бот удалён, сообщение старше лимита) → `retract_failed` с оставшимися id,
  без бесконечных повторов; transient — по `RetryPolicy`, `retry_after` канала важнее.

### Q7 / эксплуатация

`ffmpeg`, `sox`, `lame` есть на станции (проверено 18.11.2026). Модуль проверяет их в рантайме и
деградирует к тексту; установка пакетов и правки системы не выполняются. Замеры 1- и 10-минутного
файла — этап 3a-3.
