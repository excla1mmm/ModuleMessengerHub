# 05. События, правила, шаблоны

## Нормализованное событие

```json
{
  "source_id": "core.missed_call",
  "event_type": "core.missed_call",
  "severity": "info",
  "dedupe_key": "missed:mikopbx-1790944900.650",
  "occurred_at": 1790944901,
  "subject": {
    "call": {"linkedid": "mikopbx-1790944900.650", "direction": "incoming", "started_at": 1790944901, "duration_sec": 0},
    "client_number": "79689689444",
    "employees": [{"user_id": 12, "number": "233", "name": "Иванов И."}],
    "provider": null
  },
  "facts": {"reasons": [], "summary": null, "quotes": [], "scores": {}},
  "links": {"call_card": "https://pbx.example/admin-cabinet/..."},
  "attachments": []
}
```

Для голосовой почты и звонка ИИ Супервизера `attachments` содержит факт о записи (см. ниже);
у `core.missed_call` вложений нет (решение 3a-1).

- `severity`: `info` | `warning` | `critical`.
- `event_type` — `<источник>.<событие>`; каталог типов — в `02-sources.md`.
- `subject.employees[].user_id` — для `target_mode = employee` (личный чат сотрудника).
- В событии нет готового текста: текст делает шаблон под канал.

### `attachments` в событии (этап 3a)

Факты о звуке, а не готовый файл (копии записей в БД модуля не делаются):

```json
"attachments": [
  {"kind": "recording", "path": "/mountpoint/mikopbx/astspool/monitor/2026/11/18/INBOX/x.mp3"},
  {"kind": "recording", "source": "cdr", "linkedid": "mikopbx-1790944900.650", "cdr_id": 501}
]
```

- `path` — только голосовая почта (и probe-события; probe-путь обязан быть в `<module>/tmp/probe`).
- `source = cdr` — запись берётся через публичный Core REST v3 по `linkedid` (и `cdr_id`, если ИИ
  Супервизер его отдал); путь и токен скачивания в событие не попадают.
- `core.missed_call` вложений не несёт: `recordingfile` пропущенного — IVR/приветствие, а не разговор
  с клиентом (решение 3a-1). Шаблон от этого не меняется.

## Правила

Правило = какие события + фильтры + кому + как оформить.

1. Событие проходит по правилам в порядке `sort`; срабатывают **все** подходящие (не первое).
2. Совпадение: `event_type` входит в `event_types` (или `prefix.*`) и `severity >= min_severity`
   и выполнены `filters_json`.
3. Получатели правила: выбранные чаты, или чат сотрудника из события, или «сотрудник, иначе выбранные».
4. Один и тот же получатель из нескольких правил получает событие **один раз** (UNIQUE event+recipient).
5. Нет подходящих правил — событие сохраняется (видно в истории), но никуда не уходит.

Фильтры v1: сотрудники (`user_id`), направление звонка, провайдеры, внутренние звонки вкл/выкл.
Тихие часы и дайджесты — этап 4.

### Опция правила `options.attachments` (этап 3a)

```json
{"attachments": "none" | "fragments" | "recording"}
```

- **По умолчанию `none`** — для новых и для уже существующих правил. Легаси-булево `true` из API
  этапа 2 тоже читается как `none`, пока администратор не выберет режим явно: обновление модуля не
  должно начать отправлять записи само (решение 3a-1).
- Допустимые значения зависят от события: `core.voicemail` — `none|recording` (`fragments` = весь файл),
  `ai_supervisor.attention_call` — `none|fragments|recording`, `core.missed_call` — только `none`.
  Неизвестное значение трактуется как `none` (fail closed). REST-валидация enum — этап 3a-2.
- Режим фиксируется в строке Outbox при маршрутизации (`attachment_json`), как и `rendered_json`:
  последующее изменение правила не меняет уже поставленное в очередь сообщение.
- Вложения не задерживают текст: сначала текст, затем аудио отдельным сообщением (Plan/03, «Вложения»).

### Правила по умолчанию при установке
Создаются выключенными, чтобы ничего не ушло до настройки:
- «Пропущенные звонки → сотруднику, иначе общий чат»;
- «Провайдер недоступен → администраторы»;
- «Системные предупреждения (warning+) → администраторы».

## Шаблоны

Шаблон — PHP-класс на тип события (`Lib/Routing/Templates/*`), возвращает `RenderedMessage`:
заголовок, строки «ключ: значение», абзацы, цитаты, кнопки, вложения. Канал сам переводит это в свою разметку.
Тексты — из `Messages/*.php` (язык АТС). Пользовательские шаблоны с подстановками — не в v1.

Пример (пропущенный):

```
📞 Пропущенный звонок
Клиент: +7 968 968-94-44
Кому: Иванов И. (233)
02.10.2026 15:41 · входящий
ID звонка: mikopbx-1790944900.650
[Открыть журнал звонков]
```

Пример (ИИ Супервайзер, этап 3) — формат согласован с клиентом в ТЗ по `moduleaisupervisor#10`:
причины, оценка качества, краткое описание от ИИ, до 3 цитат с таймкодами, ID звонка, кнопка «Открыть звонок».

## Маскирование

`PhoneMasker` применяется при рендере, если включено в правиле или глобально: `+7 968 ***-**-44`.
В `payload_json` номер хранится полностью (нужен для фильтров), в Outbox — уже замаскированный текст.

## Реализация этапа 2 (20.11.2026)

- Шаблоны — `Lib/Routing/Templates/*` (по классу на тип события); возвращают нейтральный
  `RenderedMessage` (заголовок, строки, курсивные заметки, цитаты с таймкодами, моноширинный
  ID, `url`-кнопки, вложения для этапа 3a). Тексты — ключи `module_messenger_hub_*` из `Messages/*`.
- Router (`Lib/Routing/Router.php`): срабатывают все подходящие правила, дедупликация
  `UNIQUE(event_id, chat_id)`; событие без правил сохраняется в журнале, но никуда не уходит;
  `hub_enabled = 0` — события пишутся, отправки нет (Plan/01).
- Условия этапа 2 — сотрудники (`user_ids`), направление звонка (`directions`), провайдеры
  (`providers`), диапазон оценки качества (`quality_score` только для `ai_supervisor.attention_call`).
  Группы/отделы — To Do этапа 4 (решение Q14).
- Кнопка «Открыть звонок» (Q16, решение 20.11.2026): `payload.links.call_card`, если источник его дал;
  иначе для `ai_supervisor.attention_call` — карточка звонка модуля ИИ Супервайзер
  `{pbx_public_url}/admin-cabinet/module-a-i-supervisor/module-a-i-supervisor/index?ais_screen=calls&ais_card=<ref_id>`
  (договор ссылок модуля: `react-app/src/call-list-target.js`, префикс параметров `ais_`);
  для остальных звонков — журнал звонков ядра (поиска по `linkedid` через адрес ядро не поддерживает).
  Без `pbx_public_url` кнопка не добавляется.
