# 06. REST API v3 и интерфейс

Схема согласована 18.11.2026 и построена по правилам ядра MikoPBX (`Core/src/PBXCoreREST/Controllers`):
один ресурс — одна предметная область; статусы, проверки и служебные действия — методами того же ресурса
(`customMethods`), а не отдельными ресурсами. **Не добавлять новые ресурсы без изменения этого файла.**

## Общие правила

- База: `/pbxcore/api/v3/module-messenger-hub`. Каждый ресурс — каталог `Lib/RestAPI/{Resource}/`
  (`Controller` с атрибутами `ApiResource`, `HttpMapping`, `ResourceSecurity`; `Processor`; `DataStructure`; `Actions/`).
- В `HttpMapping` явно перечислять `collectionLevelMethods` и `resourceLevelMethods`, `customMethods` — как в ядре.
- Ответ — `PBXApiResult` (`result`, `data`, `messages`); ошибка — HTTP-код + `error_code`.
- Списки: `data = {items: [...], pagination: {limit, offset, total, has_more}}`; `limit` по умолчанию 50, максимум 200.
- Время — unix-секунды (`int`).
- Доступ: только администратор; `ResourceSecurity` — `LOCALHOST`, `BEARER_TOKEN`; в ModuleUsersUI — своя группа
  прав модуля, закрыта по умолчанию.
- Все тексты OpenAPI (теги, summary, description, параметры, поля схем) — ключи в `Messages/en.php` и
  `Messages/ru.php` (проверка скриптом skill `mikopbx-module`).
- **`POST /events` нет**: события создают только адаптеры источников внутри хаба (pull-модель).
- Секреты (токены ботов, ключ API хаба) в ответах не возвращаются никогда.

## Ресурсы

### `settings` — единственный экземпляр (как `mail-settings`) — этап 1

| HTTP | Метод | Уровень | Назначение |
|---|---|---|---|
| GET | `getList` | collection | Все настройки. Этап 1: `hub_enabled`, `events_retention_days`, `sources: {<source_id>: bool}` |
| GET | `getDefault` | collection | Значения по умолчанию (для формы) |
| PUT | `update` | collection | Полная замена настроек |
| PATCH | `patch` | collection | Частичное изменение; включение источника сбрасывает его курсор (baseline) |
| GET | `getSources` | collection (custom) | Каталог и состояние источников (аналог `providers:getStatuses`) |

`getSources` — элемент списка (названия — ключ перевода и текст, группа — для интерфейса, порядок
групп постоянный: Звонки → ИИ Супервайзер → Распознавание речи и облачный ИИ → Голосовой агент →
Связь и АТС; `update_to` — минимальная версия модуля с `/status`, для источников без неё пусто):

```json
{
  "id": "ai_supervisor.attention_call",
  "name_key": "module_messenger_hub_SourceAttentionCall",
  "name": "Звонок требует внимания",
  "group": "ai_supervisor",
  "group_key": "module_messenger_hub_GroupAiSupervisor",
  "group_name": "ИИ Супервайзер",
  "kind": "module",
  "module": "ModuleAISupervisor",
  "module_name": "ИИ Супервайзер",
  "event_types": [
    {"type": "ai_supervisor.attention_call", "name_key": "module_messenger_hub_EventTypeAttentionCall", "name": "Звонок требует внимания"}
  ],
  "mode": "poll",
  "poll_interval_sec": 60,
  "enabled": true,
  "availability": "available",
  "availability_name": "Доступен",
  "update_to": "",
  "last_poll_at": 1790944960,
  "last_ok_at": 1790944960,
  "last_error_code": "",
  "baseline_set_at": 1790900000
}
```

`availability`: `available | disabled | module_missing | module_disabled | api_forbidden | error`.

Этап 2 добавляет в `settings` поля: `pbx_public_url` (http/https или пусто — без кнопки «Открыть звонок»),
`mask_phone_default` (bool), `proxy_url` (пусто, `host:port`, `http(s)://…` или `socks5(h)://…`),
`max_ca_bundle_path` (пусто или абсолютный путь, этап 3). PUT заменяет и их; PATCH — частично.

### `events` — история событий (как `cdr`) — этап 1

| HTTP | Метод | Уровень | Назначение |
|---|---|---|---|
| GET | `getList` | collection | Фильтры: `event_type`, `source_id`, `severity`, `date_from`, `date_to`; `limit`, `offset` |
| GET | `getRecord` | resource | Одно событие с полным `payload` |
| POST | `retry` | resource (custom, этап 2) | Повторить отправки события со статусом `failed` |

Элемент: `id, source_id, event_type, severity, occurred_at, payload, created_at`; с этапа 2 —
`deliveries: [{recipient_id, bot_id, status, attempts, last_error_code, sent_at}]`.

### `bots` — боты вместе с их чатами (как `sip-providers`) — этап 2

| HTTP | Метод | Уровень | Назначение |
|---|---|---|---|
| GET | `getList`, `getRecord`, `getDefault` | collection / resource / collection | |
| POST | `create` | collection | `channel` (`telegram` \| `max`), `title`, `token` (только запись) |
| PUT / PATCH | `update` / `patch` | resource | в т. ч. `chats` (вкл/выкл, `linked_user_id`, ручной `chat_id`) |
| DELETE | `delete` | resource | |
| POST | `checkToken` | resource (custom) | Проверить токен (`getMe` / `GET /me`) |
| POST | `discoverChats` | resource (custom) | Запустить поиск чатов на 5 минут; найденные появляются в `chats` записи бота |
| POST | `sendTest` | resource (custom) | Тестовое сообщение в выбранные чаты через общую очередь отправки |

Запись: `id, channel, title, token_hint, bot_username, enabled, status, last_error_code, discovery: {active, expires_at},
chats: [{id, chat_id, chat_kind, title, linked_user_id, enabled, state, gone_reason}]`.

### `rules` — правила маршрутизации (как `outbound-routes`) — этап 2

| HTTP | Метод | Уровень | Назначение |
|---|---|---|---|
| GET | `getList`, `getRecord`, `getDefault` | | |
| POST | `create` | collection | |
| PUT / PATCH | `update` / `patch` | resource | |
| DELETE | `delete` | resource | |
| POST | `changePriority` | collection (custom) | Порядок правил |

Запись: `id, title, enabled, event_types, min_severity, filters, target_mode, chat_ids, options, priority`.

Этап 3 (MAX) ресурсов не добавляет — только `channel: "max"` в `bots`.

## Интерфейс (Volt + jQuery + Fomantic UI)

Пункт меню «Уведомления в мессенджеры» (группа `integrations`). Эталон — утверждённый дизайн
`docs/design/ModuleMessengerHub.html` (экраны, «Тексты интерфейса», «Дизайн-токены», «Компоненты», «Допущения»).
Токены и переопределения Fomantic — в `public/assets/css/module-messenger-hub.css`, всё ограничено корнем
`.module-messenger-hub`; остальная админка не затрагивается. JS — один файл на страницу в
`public/assets/js/src/`, сборка Babel (targets Chrome 50 / Firefox 45 / IE 11).

### Структура вкладок (дизайн, допущение 15)

| Вкладка | Этап | Ресурсы |
|---|---|---|
| **Уведомления** | 2 | `rules` + `settings:getSources` (состояние источника видно в строке уведомления и на карточке сценария) |
| **Журнал** | 1 | `events` (+ `settings:getSources` — имена и состояния для фильтров) |
| **Настройки** | 1–2 | `settings` (Общие), `bots` (Мессенджеры, этап 2) |

Отдельной вкладки «Источники» с переключателями **нет**: источник включается, когда на него появляется
первое уведомление (этап 2); аварийный выключатель источника есть только в `settings.sources` (API), в
интерфейсе его нет (решение 1.4 — см. `11-open-questions.md`).

### «Новое уведомление» — мастер из трёх шагов (этап 2)

Шаг 1 «Сценарий» (карточки по группам источников; сценарий недоступного модуля виден, но неактивен,
с причиной и действием) → шаг 2 «Условия» (чипы-фильтры; список условий зависит от сценария) →
шаг 3 «Куда отправить» (мессенджер, получатель: сотрудник из события / выбранные чаты / сотрудник,
иначе чаты; маскирование). Предпросмотр сообщения — сбоку. Ресурсы: `rules` (create), `settings:getSources`.

### Этап 2c — «Уведомления», мастер и «Отправка» в журнале (реализовано)

- Ресурс `rules`: `getList`, `getRecord`, `getDefault`, `create`, `update`, `patch`, `delete`,
  custom `changePriority` (collection-level, `{order: [id, …]}` — перестановка всех правил).
  Запись: `id, title, enabled, event_types, min_severity, filters, target_mode, chat_ids, chats,
  options, priority, template_key, source_id, group, last_event_at`. `priority` — это `sort`;
  правила проверяются сверху вниз.
- Условия этапа 2: `filters.user_ids`, `filters.directions` (`incoming|outgoing|internal`),
  `filters.providers` (id или username), `filters.quality_score {min,max}` — только для
  `ai_supervisor.attention_call`. Групп/отделов нет (To Do этапа 4, решение Q14). Метода
  `previewMatches` нет (решение 4).
- `options`: `mask_phone`, `attachments` (этап 3a), `retract_on_callback` (этап 2d).
  `attachments` (этап 3a-2): `none` (по умолчанию) | `fragments` | `recording`. Валидация (422 с кодом,
  поле `options`): неизвестное значение, булево, массив, `null` → `invalid_attachments_mode`; режим, при
  котором в `event_types` правила нет подходящего типа → `attachments_not_supported`. `recording` требует
  `core.voicemail` или `ai_supervisor.attention_call`; `fragments` — `ai_supervisor.attention_call`
  (у голосовой почты фрагментов нет — правило только с голосовой почтой должно сказать `recording`; в смешанном
  правиле голосовая почта уходит целым файлом); остальные типы (`core.missed_call`, провайдеры и т. д.) —
  только `none`. Маски `ai_supervisor.*` учитываются как в маршрутизации. PATCH проверяет итоговое
  сочетание (сохранённые `event_types` + присланные поля): смена типов на «без звука» при сохранённом
  режиме — 422, пока режим не станет `none`. Старое булево `attachments: true` читается как `none`,
  а правило с ним остаётся доступным для PATCH других полей.
  Запись/удаление/изменение правила сразу применяет набор путей ключа хаба (`/api/v3/cdr` появляется с
  первым включённым правилом звонка ИИ со звуком и уходит с последним) — тот же `ApiKeyReconciler`, что у
  PATCH настроек; сбой синхронизации запрос не ломает, коллектор пересчитывает набор раз в минуту.
  `retract_on_callback: {enabled: bool, window_min: 5–120, count_incoming_answered: bool}` — только для
  сценария «Пропущенный звонок»; валидируется (`window_min` вне 5–120 или не булево `enabled` — 422).
- «Уведомления»: категории в фиксированном порядке (Звонки → ИИ Супервайзер → Распознавание речи и
  облачный ИИ → Голосовой агент → Связь и АТС), оглавления только при двух и более категориях; строка — переключатель, название,
  кому/куда, время последнего подходящего события; состояние источника — только информация
  («Модуль выключен», «Модуль не установлен», «Модуль не даёт доступа к данным») без кнопок
  (решения 1–2); «…» — «Изменить»/«Удалить». Список обновляется сам каждые 30 с.
- Этап 3b-2. Категория `speech_ai` «Распознавание речи и облачный ИИ» (источники `local_stt.workers`,
  `local_stt.backlog`, `cloud_stt.incidents`, `cloud_stt.paused`, `cloud_ai.paused` — по сценарию на вид проблемы, 3b-4) стоит сразу после «ИИ Супервайзера»: та же аудитория и тот же
  ИИ-конвейер; `ai_supervisor.workers` остаётся в «ИИ Супервайзере». Статусы источника — только текст без
  кнопок: «Модуль не установлен», «Модуль выключен», «Модуль не даёт доступа к данным», а для
  `api_incompatible` — «Нужно обновить модуль до версии N» (`update_to`; пусто — «…до версии с поддержкой
  мониторинга»). Журнал и предпросмотр показывают события `/status` человеческими фразами по паре
  (`code`, `ref`) и счётчиками; сырой `code:ref` только во всплывающей подсказке строки. Пузыри
  предпросмотра для 12 типов событий строятся на примерных данных.
- Этап 3b-4. Условия status-сценариев на шаге 2 («Условия»): переключатель «Сообщать о восстановлении» (по
  умолчанию включён; выключен — recovery-тип не входит в `event_types`), для «Инциденты облачного
  распознавания» — «Важность» («Предупреждение» / «Критичный» → `min_severity`), для «Пауза облачного анализа» —
  причины паузы флажками по группам (`filters.reasons`, по умолчанию все, кроме «Ручная пауза»; пустой выбор не
  даёт перейти дальше, REST отвечает `invalid_filter`). Мастер идёт 1 → 2 → 3, предпросмотр показывает пузырь
  проблемы (с выбранной причиной) и при включённом восстановлении второй пузырь восстановления.
- Мастер «Новое уведомление» — три шага: сценарий (карточки по группам; недоступный сценарий виден,
  но неактивен с причиной) → условия (только применимые к сценарию) → куда отправить (бот, режим
  получателей, чаты, маскирование, название). Справа — живой предпросмотр сообщения в Telegram.
  Создание через `POST rules`; заголовок по умолчанию — название сценария.
- Журнал: колонка «Отправка» (`Доставлено · N из M`, `В очереди`, `Ошибка · N из M`,
  `Пропущено`, `Перезвонили`, `Не удалось удалить`); в раскрытой строке — отправки по чатам с
  названием чата/бота, статусом, кодом ошибки и кнопкой «Повторить». История удалённого бота/чата
  читается через LEFT JOIN и показывается как «Бот удалён» — без ошибки в интерфейсе.
  `POST events/{id}:retry` перезапускает только строки со статусом `failed` (свежие попытки,
  немедленная отправка, будильник воркера).
- Этап 2d (Plan/12): `deliveries[]` несут `status` (`cancelled`, `retracted`, `retract_failed`),
  `retract_reason`, `resolved_at`, `resolved_by`, `retracted_at`, `retract_last_error_code`;
  в раскрытой строке — «Перезвонили в 15:52 (Иванов И. (233))». Мастер для «Пропущенного звонка»
  показывает на шаге «Условия» переключатель удаления, окно (5–120 мин, по умолчанию 20) и вложенный
  «Считать перезвоном и дозвон клиента» (по умолчанию включён). Строка списка получает
  «… · удалять при перезвоне за 20 мин».
- Этап 3a-2: шаг 3 мастера для сценариев со звуком получает блок «Прикладывать запись» (радио): для звонка
  ИИ Супервайзера «Нет / Фрагменты с цитатами / Весь разговор», для голосовой почты «Нет / Запись»; для
  остальных сценариев блока нет, и `attachments` не отправляется. Подсказка «Запись уйдёт в мессенджер —
  за пределы АТС» видна при выбранном режиме, режим по умолчанию «Нет». Предпросмотр дополняется
  аудио-пузырём (для фрагментов — по одному на фрагмент с «Фрагмент 1 из 2 · 0:12»; для разговора/почты —
  «Запись · 6:42»); числа — образцовые, не реальные данные. Журнал: в раскрытой строке под статусом каждой
  отправки — «Запись: отправлена | отправлено N из M | вместо файла добавлена пометка в сообщении |
  пропущена · причина | не отправлена · причина | в очереди»; причины словами («нет конвертера аудио»,
  «файл слишком большой или длинный», «нет записи», «нет цитат», «неизвестный исход», «мессенджер
  недоступен…»); сырой код (`attachment.*`, `delivery.uncertain`, `http.*`) — только во всплывающей
  подсказке (`title`). Неизвестный код показывается как есть. `GET events` / `events/{id}` отдают в
  `deliveries[].attachment` минимум: `{state: none|pending|sent|partial|skipped|failed, code, parts, sent,
  skipped, note: none|pending|sending|sent|failed}` — без путей, токенов частей и id аудио-сообщений.
  «Заменено пометкой» = вложение пропущено, а короткая строка «Запись доступна в АТС» ушла в текст
  (`note = sent`).
- Пробы на стенде помечаются в событии (`payload.probe`), в журнале меткой «проба», а в сообщении —
  курсивной строкой «Тестовая проба модуля…».

### Этап 2b — «Настройки → Мессенджеры» (реализовано)

- Список ботов карточками: канал, имя, `@username`, число чатов, статус («Работает», «Токен отклонён»,
  «Не проверили токен», «Выключен»); раскрытие показывает чаты, привязку сотрудника, переключатель
  и действия «Подключить чат», «Отправить тест», «Заменить токен и настройки».
- «Добавить бота»: канал, название, токен; «Проверить» сохраняет бота и сразу проверяет токен
  (отклонённый токен сохраняется со статусом и причиной); «Сохранить и подключить чат» открывает
  поиск. «Отмена» удаляет черновика, созданного кнопкой «Проверить».
- «Подключить чат»: инструкция, обратный отсчёт 5 минут, найденные чаты с отметками; уже подключённые
  помечены «Есть», новые — «Новый»; «Сохранить выбранные» включает отмеченные чаты, «Искать ещё 5 минут»
  перезапускает сеанс, «Остановить поиск» закрывает его. Состояния: идёт поиск / найдено / время вышло /
  ничего не найдено / ошибка (в т. ч. «у бота настроен вебхук»).
- «Отправить тест»: ставит сообщение в очередь, показывает результат по каждому чату
  («Доставлено» / «В очереди» / «Ошибка» с кодом) и «Повторить» для неудачных; тест идёт тем же путём,
  что и настоящие уведомления.
- «Общие»: срок хранения, адрес АТС (с подсказкой про внутреннюю сеть), «Скрывать номера», прокси.
  Изменения сохраняются сразу (PATCH), ошибки полей подсвечиваются.
- **MAX (с этапа 3c):** карточка и модалка включены, `channel: max` принимается API; подсказка про
  токен (business.max.ru, модерация до 48 ч), поиск чатов («нажмите "Начать" или добавьте бота в
  группу»), состояние «Не удалось проверить сертификат MAX» (`ca_error`) со ссылкой на
  `max_ca_bundle_path`, подсказка для `max.405.webhook_set` (`DELETE /subscriptions`). Код
  `channel_not_available` остаётся только на случай, если в сборке не зарегистрирован адаптер канала.
- Бот может быть в статусе `new`, `ok`, `token_invalid`, `ca_error` (не удалось проверить сертификат
  MAX) или `error`; успешная отправка возвращает статус `ok`. `status` объявлен в схеме перечислением,
  `channel` обязателен при создании и неизменяем после него (в `:checkToken` чужой `channel` в теле —
  422 `channel_immutable`: иначе сохранённый токен одного мессенджера уходил бы в другой).
- Токен MAX не имеет документированного формата, поэтому проверяется как печатный ASCII без пробелов
  (8–512 символов): он попадает в значение заголовка `Authorization`, где иное недопустимо.
- Создание с токеном уже подключённого бота сохраняет запись со статусом `token_invalid` и кодом
  `other_bot` (как у Telegram) — UI показывает предупреждение «этот бот уже подключён».
- Вложенные чаты можно передать и в `POST /bots` (как в `PATCH`); невалидный чат откатывает создание
  бота целиком.
- **Отступление от макета (осознанно):** шаг 3 мастера получил колонку предпросмотра (как шаг 2).
  Правило адресуется одному боту, а бот выбирается на шаге 3, поэтому без колонки нельзя показать
  вариант MAX до сохранения правила; сценарии без условий идут 1 → 3 и иначе не увидели бы
  предпросмотр вовсе.

### Этап 1 (текущая реализация)

- Вкладка **Журнал**: фильтры (период, тип события, источник, важность), таблица (Время / Событие /
  Кратко / Важность; колонка «Отправка» скрыта до этапа 2), раскрытие события с полями payload,
  постранично (50 на страницу). Состояния из дизайна: загрузка (скелетон; при обновлении строки
  остаются под полупрозрачной заливкой), ошибка с «Повторить» (баннер, если данные уже на экране,
  иначе центрированная заглушка с кодом), «Событий пока нет», «Нет событий по выбранным фильтрам»
  (с числом таких событий за всё время), длинные значения (2 строки с многоточием и подсказкой).
  Список обновляется сам каждые 30 с. Недоступность источника не скрывается: в фильтре «Все источники»
  каждый источник помечен состоянием («доступен», «модуль выключен», «модуль не установлен», «нет
  доступа», «ошибка»).
- Вкладка **Настройки → Общие**: предупреждение о передаче данных (всегда виден), «Хранить журнал,
  дней» (1–365), «Изменения сохраняются сразу» (PATCH на изменение, тост). Секция «Мессенджеры» и
  поля этапа 2 (адрес АТС, «Скрывать номера», прокси) до этапа 2 не показываются.
- Вкладка **Уведомления**: показана с пустым состоянием из дизайна **без** кнопки «Новое уведомление»
  и с пометкой, что создание уведомлений появится в следующей версии (чтобы структура из трёх вкладок
  совпадала с дизайном и было видно, зачем модуль).
- `hub_enabled` — аварийный выключатель уровня API, в интерфейсе не показывается.

JS: `public/assets/js/src/module-messenger-hub-index.js`. Тексты — только через переводы
(`module_messenger_hub_*`), раздел «Тексты интерфейса» дизайна.

### Отступления от утверждённого дизайна (решение пользователя 20.11.2026, приоритетнее макета)

- **Никаких действий с ключами в интерфейсе.** Кнопки «Выдать доступ» нет. Ключ хаба полностью автономен:
  создаётся, обновляется и при необходимости пересоздаётся сам. Если модуль-источник сам не пускает ключ хаба —
  только информационный текст «Модуль не даёт доступа к данным».
- **Хаб не управляет другими модулями.** Кнопки «Включить» нет — только информация «Модуль выключен».
- **Подсказки «за прошлую неделю подошло бы N» нет**, метода `rules:previewMatches` нет.
- Условия правил в этапе 2 — сотрудники, направление звонка, провайдеры, оценка качества для
  «звонок требует внимания». Группы/отделы — To Do этапа 4 (ModuleUsersGroups).
