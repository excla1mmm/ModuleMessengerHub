# 07. Безопасность и персональные данные

## Токены ботов

- Хранятся только в `m_MessengerHubBots.token` в БД модуля (файл доступен root/www АТС).
  Шифрование ключом, лежащим на той же АТС, не даёт реальной защиты — не делаем вид, что защищаем;
  вместо этого строго контролируем выход наружу.
- REST API и интерфейс **никогда** не возвращают токен: только `token_hint` (последние 4 символа).
  Замена токена — новым значением; прочитать старый нельзя.
- Telegram передаёт токен в URL → `HttpTransport` не пишет URL, заголовки и тела запросов в лог;
  ошибки нормализуются в коды (`telegram.403.blocked`, `max.attachment_not_ready`, `http.timeout`).
- Тест-контракт: ни один ответ API, ни одна строка лога, ни `last_error_code` не содержат токен
  (`Tests/check-*-secret-*`).

## Права

- Все ресурсы модуля — только администратор (ModuleUsersUI: закрыто по умолчанию).
- Собственный ключ API хаба (решение Q1, уточнено 23.11.2026): `full_permissions='0'`, в `allowed_paths` — только
  пути включённых источников со значением `read`, **кроме двух путей ModuleLocalSpeechToText `/workers` и
  `/jobs` со значением `admin`**; `write` не выдаётся никогда, `full_permissions` всегда `0`. Ключ **привязан к
  localhost** (`networkfilterid = 'localhost'`: `TokenValidationService::checkNetworkFilter` пропускает
  только `127.0.0.1` и `::1`, а хаб ходит только с самой АТС); фильтр и уровни выставляются при создании и при
  каждой синхронизации и починке, `verify()` считает иной фильтр или уровень нездоровым и чинит запись на месте
  (тот же id и секрет, Q15). Открытое значение — секрет
  хаба наравне с токенами ботов: не отдаётся API, не логируется. В ядре хранится только bcrypt-хэш.
  Описание ключа в списке ключей ядра: «ModuleMessengerHub (read-only sources)». Удаляется при отключении хаба.
- **Почему `admin` на двух путях Local STT и какой риск принят.** Модуль Local STT отдаёт `/workers` и `/jobs`
  ключу API только при значении `admin` на этом пути (`WorkerRequestContext::isAdministrator`; чтение
  состояния воркеров и очереди без `/status` другим способом недоступно, а `/status` в этом модуле не
  выпускается — решение Q10/Q11 от 23.11.2026). Хаб шлёт на эти пути только `GET` и читает из ответа лишь
  `id`, `status`, `last_seen`, `created_at` (воркеры) и число/`created_at` ждущих задач (`/jobs`); имена, адреса,
  ключи воркеров и `call_id` задач не читаются и не сохраняются, тела ответов не логируются. Значение `admin`
  модулем Local STT трактуется как право управлять этими ресурсами (создание воркеров, повтор и удаление
  задач), поэтому ключ хаба, утекший из `m_MessengerHubSettings`, дал бы такое управление, но только с
  localhost АТС (привязка выше) и только на этих двух путях; другие ресурсы Local STT и все остальные модули по-прежнему
  недоступны (`admin` не распространяется на соседние пути: ядро сверяет путь точно). Риск принят пользователем
  23.11.2026: воспользоваться ключом может только тот, кто уже выполняет код на самой АТС (root, другой модуль),
  а у него и без ключа доступ шире — базы Local STT, процессы, файлы; копия ключа из резервной копии вне АТС
  бесполезна (привязка проверена на станции: снаружи 401, с `127.0.0.1` — 200).
- **Этап 3a: `/api/v3/cdr` в ключе — только пока включено правило с вложениями.** Путь добавляется в
  `allowed_paths` со значением `read` только если одновременно включён источник ИИ Супервизора (модуль
  доступен) **и** есть включённое правило с `attachments != none` для `ai_supervisor.attention_call`;
  при выключении правила/источника путь снимается синхронизацией на месте (Q15, раз в минуту). Пока
  путь есть, ключ может перечислить все CDR и получить одноразовые `download_url`/`playback_url` к
  любой записи, а не только к звонку «требует внимания»: у ядра нет ACL по звонку для ключа. Хаб
  использует путь только в `RecordingLocator`; URL с токеном не логируется и не отдаётся REST. При
  утечке дампа БД модуля в этот период ключ даёт доступ ко всем записям АТС.
- **Этап 4s-A: `/api/v3/cdr` и `/api/v3/sip` в ключе — пока включены источники безопасности.** Источник
  `core.toll_fraud` читает список CDR (те же поля звонка, без записей и без `download_url`: URL не
  запрашиваются и в события не попадают), поэтому путь `/api/v3/cdr` со значением `read` есть в ключе,
  пока источник включён (по умолчанию новые источники включаются, как и все остальные). Риск тот же,
  что у этапа 3a: пока путь в ключе, утёкший дамп БД модуля даёт перечисление CDR и одноразовые ссылки
  на записи; администратор, которому это неприемлемо, выключает источник `core.toll_fraud` — путь
  снимается синхронизацией на месте (Q15). Источник `core.sip_auth_failures` читает
  `GET /api/v3/sip/{extension}:getAuthFailureStats` (только `GET`, счётчики неудачных SIP-авторизаций
  одного номера), поэтому путь `/api/v3/sip` со значением `read` есть в ключе, пока источник включён;
  POST-методы этого ресурса (`processAuthFailures`, `clearAuthFailureStats`, `forceCheck`) требуют
  `write` и ключу недоступны. IP-адреса источников попыток уходят в событие только когда администратор
  включил правило для `core.sip_auth_failures`.

## Персональные данные

- Во внешний мессенджер уходят номер клиента, имя сотрудника, тексты (сводки ИИ, цитаты), записи.
- По умолчанию хаб **выключен**, правила созданы выключенными.
- В настройках — явное предупреждение о передаче данных во внешний сервис.
- Маскирование номера (глобально и в правиле), отключение вложений в правиле.
- **Записи и временные файлы (этап 3a).** Скачанные из Core/S3 записи и сконвертированные MP3 лежат
  только в `<module>/tmp/attachments` (0700) до доставки/окончательного отказа; уборщик удаляет забытое
  старше 6 ч. В БД модуля хранятся только пути (`attachment_json`, `files_json`), не копии звука.
  MAX upload-токен хранится в `delivery_parts_json` и не попадает в REST/журнал (только состояние/код).
- История в БД модуля хранится ограниченный срок (по умолчанию 30 дней).

## Сеть

- Исходящий HTTPS к `api.telegram.org`, `platform-api2.max.ru` и адресам загрузки MAX: по факту станции (21.11.2026) `POST /uploads` отдаёт CDN-хост платформы
  (`*.okcdn.ru`, сертификат `*.mycdn.me`), а не `*.max.ru`; токен бота уходит только на `platform-api2.max.ru`
  и `*.max.ru`, на CDN — никогда (адрес загрузки сам несёт авторизацию).
- Прокси HTTP/HTTPS/SOCKS5 в настройках.
- TLS всегда с проверкой сертификата; для MAX — корневой сертификат НУЦ Минцифры (файл в модуле
  или путь в настройках).

## Входящие данные

Тексты из событий (имена, расшифровки, названия чатов) — недоверенные: экранирование под разметку
канала, ограничение длины, без интерпретации как команд.
