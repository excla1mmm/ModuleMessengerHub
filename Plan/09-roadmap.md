# 09. Этапы

Каждый этап заканчивается рабочим, устанавливаемым модулем. Этап закрыт, когда выполнены все критерии
и пройдены `php Tests/run-all.php` и сборка пакета. Отметку о закрытии ставить здесь.

## Этап 0 — каркас ✅ (18.11.2026)

- Структура модуля, `module.json`, `composer.json`, установщик, пустой `MessengerHubConf`,
  модель `MessengerHubSettings`, переводы регистрационных ключей во всех 29 языках.
- План (`Plan/`), документация для агентов (`AGENTS.md`, `CLAUDE.md`, `docs/`), README.
- Сборка `scripts/package-module.sh`, тесты `Tests/run-all.php`, CI `.gitlab-ci.yml`, `.github/workflows/build.yml`.

## Этап 1 — каналы и доставка (v1, первая установка у клиента)

Задачи:
1. Модели `Bots`, `Recipients`, `Events`, `Outbox`, `DiscoverySessions`.
2. `HttpTransport` (curl, таймауты, прокси, TLS/CA, без логов с секретами).
3. `TelegramChannel`, `MaxChannel` по контракту `ChannelInterface` (`checkToken`, `discoverChats`, `send`, `limits`).
4. Outbox, `DeliveryService`, `RetryPolicy`, `RateLimiter`, воркер `WorkerMessengerHubDelivery`.
5. REST: `/settings`, `/bots`, `/bots/{id}:check`, `/chat-discoveries`, `/recipients`, `/test-messages`, `/deliveries`.
6. Интерфейс: вкладки «Боты», «Получатели», «История», «Настройки».

Критерии приёмки:
- [ ] Бот Telegram и бот MAX подключаются по токену, неверный токен — понятная ошибка.
- [ ] «Подключить чат» находит группу с добавленным ботом и личный диалог после `/start` / «Начать».
- [ ] Тестовое сообщение приходит в каждый выбранный чат обоих мессенджеров.
- [ ] Мессенджер недоступен → сообщение уходит после восстановления; 429 обрабатывается по `retry_after`.
- [ ] Удалённый из чата бот → получатель `gone`, без бесконечных повторов.
- [ ] Токен не возвращается API, не встречается в логах и кодах ошибок (контрактный тест).
- [ ] TLS к MAX проходит с проверкой сертификата.

## Этап 2 — события ядра

1. `SourceInterface`, `SourceRegistry`, `m_MessengerHubSourceState`, воркер `WorkerMessengerHubCollector`.
2. Router: правила, получатели, шаблоны; модель `Rules`; REST `/rules`, `/sources`; вкладки «Правила», «Источники».
3. Источники: пропущенный звонок (AMI), провайдер (хук), системные предупреждения (опрос advice),
   голосовая почта (AMI), запуск АТС (хук).
4. Привязка личного чата к сотруднику (`linked_user_id`), `target_mode = employee`.

Критерии:
- [ ] Пропущенный входящий приходит сотруднику, которому звонили, если у него привязан чат; иначе — в общий чат.
- [ ] Звонок, отвеченный любым плечом, не считается пропущенным.
- [ ] Провайдер отключился → одно сообщение; флаппинг не даёт лавины.
- [ ] Новое системное предупреждение → одно сообщение; повторный опрос не дублирует.
- [ ] После включения источника старые события не рассылаются.

## Этап 3 — события модулей MIKO (pull через их REST API)

1. Механизм ключа API хаба для чтения (решение Q1).
2. Адаптеры: ИИ Супервайзер (звонок требует внимания, воркер офлайн), Local STT (воркер офлайн,
   очередь без воркеров), Cloud STT (инцидент, остановка), Cloud AI (пауза), VoiceAgent (заявка на перезвон,
   агент недоступен).
3. Вложения: запись разговора / фрагменты, конвертация в MP3.
4. Шаблон «звонок требует внимания» по ТЗ `moduleaisupervisor#10`.

Критерии:
- [ ] Модуль-источник не установлен/выключен → источник «недоступен», хаб работает.
- [ ] Звонок «клиенту не помогли» из ИИ Супервайзера приходит один раз, повторный анализ не дублирует.
- [ ] Заявка на перезвон VoiceAgent приходит один раз.
- [ ] Ни один модуль-источник не изменён.

## Этап 4 — удобство

Тихие часы, сводные сообщения при лавине, дайджесты за день, фильтры по провайдерам/направлениям,
статусы сотрудников онлайн/офлайн, шаблоны с подстановками.

## Этап 5 — безопасность АТС

Вход в веб-интерфейс, баны fail2ban, срок SSL-сертификата — без изменений ядра (см. 02 и Q3).
