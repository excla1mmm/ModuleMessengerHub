# 11. Открытые вопросы и решения

Формат: вопрос → что известно → что нужно сделать. Решённое переносится в раздел «Решения» с датой.

## Открытые

**Q3. Вход в систему без изменения ядра.** Ядро вызывает `onAfterExecuteRestAPIRoute(Micro $app)` у модулей
после каждого REST-маршрута (`PBXCoreREST/Providers/RouterProvider.php:735-740`), передавая приложение целиком.
Что из него видно для `auth:login` (маршрут, код ответа, пользователь, IP) — проверить на станции
**установленным хабом** с пробным хуком (этап 5). Хук вызывается на каждом REST-запросе — реализация обязана
быть дешёвой. Запасной путь — syslog-строка `Successful login: User=… From=…` (`LoginAction.php:229`);
путь к журналу на станции не найден быстрым поиском (каталог логов большой) — уточнить в этапе 5.

**Q6. Каталог сторонних источников.** Для ModuleBackup, ModuleGetSsl, ModuleVPN, ModuleAmoCrm,
ModuleBitrix24Integration, ModuleRemoteSupport, ModuleQueueCallBack — проверить, есть ли у них читаемый API.
Без API источник не делаем.

**Q9 — решён 21.11.2026 на тестовом боте (этап 3d).** Подтверждено живым MAX:

- «бот удалён из группы» → `POST /messages` **404** `{"code":"error.not.found"}` → `recipient_gone`,
  `max.404.not_found`, чат `gone`, повторов нет;
- «пользователь заблокировал бота» → **403** `{"code":"chat.denied","message":"Key:
  error.dialog.suspended, …"}` → `recipient_gone`, `max.403.chat_denied`, чат `gone`;
- вебхук-подписка **не даёт 405**: `GET /updates` отвечает `200` с пустой страницей, поэтому хаб
  проверяет `GET /subscriptions` на первой пустой странице сеанса и только тогда ставит
  `max.405.webhook_set`;
- лимит 4000 считается по длине строки `text` вместе с тегами (400 `proto.payload`);
- удаление свежего сообщения работает; **возрастной лимит** не выяснен — сообщения старше суток на
  тестовом боте нет (в интерфейсе так и написано);
- `Retry-After` в 429 за сессию не встретился; может ли бот писать первым — не проверялось.

Подробности и таблица сопоставления — `03-channels.md`, раздел MAX.

| 19.11.2026 | **Ключ хаба переживает обновление модуля (следствие Q15).** Обновление пакета в ядре идёт как disable → замена файлов → enable, поэтому прежнее «удалить ключ при отключении» (Q1) меняло id ключа при каждом обновлении. Деинсталляция (этап 3a-2): `PbxExtensionSetup::uninstallModule` вызывает `HubApiKey::remove()` и удаляет запись из `m_ApiKeys`. Ядро зовёт `uninstallModule($keepSettings = true)` и при обновлении пакета — тогда ключ не трогаем (id и секрет сквозные), удаляем только при настоящем удалении без сохранения настроек; сбой удаления логируется кодом и деинсталляцию не ломает. Осиротевшие записи с описанием хаба по-прежнему подчищаются в `create()`. |
