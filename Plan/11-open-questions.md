# 11. Открытые вопросы и решения

Формат: вопрос → что известно → что нужно сделать. Решённое переносится в раздел «Решения» с датой.

## Открытые

**Q19. Автор изменения конфигурации (этап 4s-C).** Сообщение ядра
`{source: ModelsBase->sendChangesToBackend, model, recordId, action, changedFields}`
(`src/Common/Models/ModelsBase.php:393-414`) не содержит пользователя, сессию или адрес клиента: запись через
REST-ключ и через кабинет выглядят одинаково. Поэтому событие `core.config_changed` не сообщает, кто изменил
настройки. Чтобы получить автора, нужен либо новый контракт ядра (поле в сообщении модели), либо разбор
syslog/аудита запросов — оба варианта требуют правки ядра или отдельного исследования на станции. Пока
автор не указывается; вопрос — к следующей версии ядра.

**Q20. Сроки особенностей (features) лицензии.** В документе лицензии дата окончания есть только у продукта
(`product.expired`); у вложенных `feature` в контракте есть лишь `name`, `count`, `counteach`, `captured`
(`sites/admin-cabinet/assets/js/src/PbxExtensionModules/pbx-extension-module-keycheck.js:355-364`). Источник
`core.license_expiring` поэтому напоминает только о продуктах. Если сервер лицензий начнёт отдавать даты
особенностей — добавить их в источник. Проверить на станции с реальной лицензией: полный список полей
документа (в репозитории ядра образца нет, класс `MikoPBX\Service\License` скомпилирован).

**Q21. Лицензия без ключа и недоступный сервер лицензий.** `GetLicenseInfoAction` отвечает 400 с
`result: false` и для пустого/неверного ключа, и когда сервер лицензий недоступен; хаб не может отличить
эти случаи (REST-обёртка отдаёт только код). Решение 4s-C: 400 трактуется как «документа лицензии нет» —
событий нет, источник не считается сбойным (иначе нелицензированные АТС постоянно показывали бы ошибку).
Цена: недоступность сервера лицензий этим источником не диагностируется (её видно в кабинете ядра на
странице лицензии). Если понадобится различать — нужен отдельный признак в ответе ядра.

**Q3. Вход в систему без изменения ядра.** Ядро вызывает `onAfterExecuteRestAPIRoute(Micro $app)` у модулей
после каждого REST-маршрута (`PBXCoreREST/Providers/RouterProvider.php:735-740`), передавая приложение целиком.
Что из него видно для `auth:login` (маршрут, код ответа, пользователь, IP) — проверить на станции
**установленным хабом** с пробным хуком (этап 5). Хук вызывается на каждом REST-запросе — реализация обязана
быть дешёвой. Запасной путь — syslog-строка `Successful login: User=… From=…` (`LoginAction.php:229`);
путь к журналу на станции не найден быстрым поиском (каталог логов большой) — уточнить в этапе 5.

**Q6. Каталог сторонних источников.** Для ModuleBackup, ModuleGetSsl, ModuleVPN, ModuleAmoCrm,
ModuleBitrix24Integration, ModuleRemoteSupport, ModuleQueueCallBack — проверить, есть ли у них читаемый API.
Без API источник не делаем.

**Q9 — решён 21.11.2026 на тестовом боте (этап 3d).** Подтверждено живым MAX:

- «бот удалён из группы» → `POST /messages` **404** `{"code":"error.not.found"}` → `recipient_gone`,
  `max.404.not_found`, чат `gone`, повторов нет;
- «пользователь заблокировал бота» → **403** `{"code":"chat.denied","message":"Key:
  error.dialog.suspended, …"}` → `recipient_gone`, `max.403.chat_denied`, чат `gone`;
- вебхук-подписка **не даёт 405**: `GET /updates` отвечает `200` с пустой страницей, поэтому хаб
  проверяет `GET /subscriptions` на первой пустой странице сеанса и только тогда ставит
  `max.405.webhook_set`;
- лимит 4000 считается по длине строки `text` вместе с тегами (400 `proto.payload`);
- удаление свежего сообщения работает; **возрастной лимит** не выяснен — сообщения старше суток на
  тестовом боте нет (в интерфейсе так и написано);
- `Retry-After` в 429 за сессию не встретился; может ли бот писать первым — не проверялось.

Подробности и таблица сопоставления — `03-channels.md`, раздел MAX.

**Q17. Правило нерабочего времени в событии `core.call_out_of_hours`.** Ядро уводит звонок в контекст
`work-time-set-var-<id>` / `playback-exit` и вызывает `Gosub(dial_outworktimes,${EXTEN},1)`
(`src/Core/Asterisk/Configs/ExtensionsOutWorkTimeConf.php:161-163`, `initRuleAppData()` там же), но id и
описание правила в данные события не попадают: lua собирает поля из каналов
(`src/Core/Asterisk/Configs/lua/extensions.lua:1845-1867`) и знает только `EXTEN`/`FROM_DID`. Сейчас хаб
пишет `rule_id = null`, `rule_name = ''` и ничего не выдумывает. Варианты: (а) принять ограничение —
тип события и клиент уже достаточны; (б) попросить ядро (или его dialplan-генератор) класть id правила в
переменную канала, которую lua добавит в событие (изменение ядра — запрещено правилами хаба, значит это
задача проекта ядра, а не модуля). Решение за пользователем; до него — вариант (а).

**Q18. Что считать «клиент не дождался» в очереди (проверить на станции).** Отказ от ожидания источник
`core.queue_abandoned` определяет как «плечо очереди закончилось и `queue_answer` для этого id не было».
Вопросы к живому поведению ядра: (1) при переводе из очереди на `timeout_extension` (без ответа агента)
событие будет выглядеть как отказ от ожидания — так ли это по смыслу сценария; (2) всегда ли `queue_answer`
публикуется, когда агент снял трубку (в т. ч. при ответе после перевода/подхвата), иначе будут ложные
срабатывания; (3) какие значения приходят в `dialstatus` (`QUEUESTATUS`) при снятии трубки и при таймауте —
сейчас хаб их не использует, но по ним можно уточнить вердикт. Нужен один тестовый звонок в очередь на
станции с включённым источником и разбор журнала (`HubLogger`, `m_MessengerHubEvents`).
